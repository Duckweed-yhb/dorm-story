## 一、角色定位（一句话）

负责把**游戏化闭环的"动作"**做出来：值日排班（规则版）、提醒、打卡，以及后续协作模块，让"做了事 → 有反馈"真正发生。

## 二、全周期职责

| 阶段 | 主责事项 |
|---|---|
| 阶段1（9/25–10/1） | 值日排班（规则版）、值日提醒、共同打卡 |
| 阶段2（10/2–10/8） | 共享日历、宿舍费用分摊 |
| 阶段3（10/9–10/13） | 配合丙：AI 自动排班的规则兜底与数据接入 |
| 阶段4（10/14–10/15） | 全流程回归、订阅消息节奏核对 |
| 阶段5（10/16–10/17） | 配合丙核对材料 |

## 三、阶段1 逐日任务（9/25–10/1）

| 日期 | 任务 | 验收标准 |
|---|---|---|
| 9/25 | 熟悉工程与数据模型；设计 `duty` 集合字段（dormId/date/memberId/status） | 数据模型与甲对齐，入库脚本可跑 |
| 9/26–27 | 规则版排班算法（轮转 + 公平性：上次值日者优先排后）+ 排班页 | 输入成员名单可生成一周排班，无重复冲突 |
| 9/28 | 值日提醒：订阅消息 + 定时触发器初探（每日提醒） | 到点能推送，授权流程可跑通 |
| 9/29 | 共同打卡页 + 打卡记录写入 `checkin` | 打卡成功落库、当日状态可见 |
| 9/30 | 值日完成 / 打卡 → 调用丙 `addExp` 联动；完成状态回写 | 完成动作能获得经验值 |
| 10/1 | 最小闭环联调：值日→完成→打卡→经验值变化可见 | 闭环跑通，无阻断性 bug |

## 四、负责的数据集合与对外接口（契约）

**集合**：`duty`（值日·日期·成员·状态）、`checkin`（打卡）、`announcement`（公告）、`expense`（费用）、共享日历事件

**对外提供（云函数）**：
- `scheduleDuty` / `getDuty`（排班与查询）
- `doCheckin` / `getCheckin`（打卡与查询）
- 阶段2：费用分摊 `splitExpense`、日历事件

**依赖别人**：值日/打卡完成 → 调丙 `addExp`；排班数据给甲首页回显；全局框架/组件用甲的。

## 五、与队友的协作点

- **对甲**：值日、打卡页面嵌入甲搭的 tab 与公共组件；排班结果回显到首页。
- **对丙**：所有"完成行为 → 经验值"都统一走丙的 `addExp`，你只传 `action` 与 `dormId`，不要自己算 XP。
- **对齐方式**：订阅消息模板 ID、定时触发器配置统一登记到 docs，避免各自踩坑。

## 六、技能与学习重点（对应 docs/零基础项目学习路线.md）

- 必学：阶段二（重点）——云开发、云函数、定时触发器、订阅消息，这是你的主战场。
- 简学：阶段一（只需能写页面调用云函数）。

## 七、风险与兜底

- **订阅消息权限/模板未通过** → 先做页面内提醒兜底，订阅推送后置到阶段4。
- **排班算法边界**（成员请假/退出）→ 阶段1 只做「规则轮转」最小版，异常入参返回可读错误，不崩。
- **定时触发器不稳定** → 提醒以「进页面主动刷新 + 订阅推送」双保险，不依赖单一时机。

## 八、阶段1 目标（验收口径）

> 宿舍成员能「查看本周值日 → 值日完成 → 共同打卡」，每次完成动作都会转化为经验值，反馈可见。
> 规则版排班可用、可替换（为阶段3 AI 排班留出接口位）。
